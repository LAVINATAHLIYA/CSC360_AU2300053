## What I Understood

### RGB Colour Model

- Every pixel in an RGB image stores three values: **Red, Green, Blue**
- Each channel uses 8 bits → values from 0 to 255 (256 possible levels)
- 0 means none of that colour, 255 means maximum intensity
- Combining all three channels: `(255, 255, 255)` = white, `(0, 0, 0)` = black, `(255, 0, 0)` = pure red
- 24-bit RGB images can represent approximately 16.7 million distinct colours

### RGBA — Adding the Alpha Channel

- RGBA adds a fourth channel — **Alpha** — which controls pixel transparency
- Alpha range: 0 = completely transparent, 255 = fully opaque
- Used in images with transparent backgrounds (PNG), UI overlays, text rendering with smooth edges
- Allows compositing — placing one image over another with partial visibility

### Storing Pixels as 32-bit Integers

- 4 channels × 8 bits = **32 bits = 4 bytes = one `int32`**
- All four channel values packed into a single integer for efficiency
- Supports ~4.29 billion possible colour + transparency combinations
- Convenient for processing with standard 32-bit CPU operations

### Channel Arrangements (RGBA / ARGB / BGRA / ABGR)

- Different graphics systems arrange the four channels differently in memory:
  - **RGBA** → used by OpenGL, WebGL, HTML5 Canvas, PNG
  - **ARGB** → used by Java AWT, some desktop graphics libraries
  - **BGRA** → used by DirectX, Windows GDI
  - **ABGR** → used in some specialized rendering systems
- Using the wrong format causes incorrect colours — red and blue channels swap, producing weird-looking images

### Endianness — Big Endian vs Little Endian

- **Endianness** = the order bytes of a multi-byte value are stored in memory
- **Big Endian** → Most Significant Byte at the lowest address (network byte order)
- **Little Endian** → Least Significant Byte at the lowest address (used by Intel/AMD, most modern CPUs)
- Example: `0xAARRGGBB` on a Little Endian machine is stored in memory as `[BB, GG, RR, AA]`
- An ARGB integer in Java can appear as BGRA bytes on a Little Endian system — important when doing low-level pixel manipulation

## My Reflection

- Packing four channels into one 32-bit integer was a simple idea but very elegant — it makes pixel operations faster and uses memory efficiently
- I never thought about why the same image might look wrong on different systems — endianness and channel order differences are the actual reason
- The ARGB vs RGBA distinction matters a lot in Java — Java's `BufferedImage` uses ARGB by default, so if I try to interpret its pixel data as RGBA, I'll get wrong colours
- For the bird counting project, understanding pixel storage will help when I read individual pixel values to compare them and apply filters in Java

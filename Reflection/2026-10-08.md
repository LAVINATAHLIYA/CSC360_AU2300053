## What I Understood

### Exception Handling in JavaFX

- Exceptions should be caught and shown to the user through dialog boxes, not printed to the console
- `Alert` in JavaFX (`Alert.AlertType.ERROR`) is the right way to display error messages
- Never silently swallow exceptions — at minimum, log the error so it can be investigated
- Wrapping risky operations (file reading, parsing, database calls) in try-catch prevents application crashes

### Proper Logging with `java.util.logging`

- `System.out.println` is for quick debugging, not for production code
- `java.util.logging.Logger` provides log levels: `SEVERE`, `WARNING`, `INFO`, `FINE`, `FINEST`
- Using levels lets you filter what gets recorded — in production you might only log `WARNING` and above
- Log messages should be meaningful: include what failed, where, and relevant data values

### Maven Build Review

- `pom.xml` must specify the correct Java version, group ID, artifact ID, and dependencies
- Running `mvn clean compile` checks for compilation errors
- Running `mvn clean package` produces the JAR — the actual deliverable
- Committed binary files (`target/`, `.class`) must be excluded via `.gitignore`

### Code Review Practices

- Reading someone else's code carefully helps catch bugs before they become problems
- Good naming makes code self-documenting — a reviewer shouldn't need comments to understand a method
- Consistent formatting, proper indentation, and no unused imports are signs of professional code
- Reviewing code also helps me learn patterns and approaches I hadn't thought of myself
